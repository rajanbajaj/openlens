# Release plan: v0.5.13 (O(1) frontier depth kills crawler CPU)

Target: release server (self-hosted runner `openlens-release`).
Mechanism: tag `v0.5.13` triggers
[.github/workflows/release.yml](../../.github/workflows/release.yml).

## What's in this release

- **Hot-loop fix**: `PersistentFrontier.__len__` (checked per
  crawled URL) used Redis `counts()`, a full meta-key scan per call
  — O(N^2) over the ~62k backlog. New `queue_depth()` fast path
  (two `ZCARD`s) restores the pre-Redis per-URL cost. `counts()`
  stays for the dashboard; old fakes keep working via fallback.
- 5 new tests (3 run offline, 2 live-Redis behind
  `OPENLENS_TEST_REDIS_URL` like the existing live suite).

## Pre-release checklist

- [ ] `git status` shows only the files below (plus this plan).
- [ ] No env/config changes; no `-v` volume wipes.
- [ ] Backend gates green (1711 passed, ruff + mypy clean).

## Release steps

1. Tag `v0.5.13` and push `main` + tag (tags never move).
2. Watch the `release` workflow (`concurrency: release-production`).
3. Gates: `/healthz`, frontier status, search probe, both frontends.

## Post-deploy verification (on the server)

- `docker stats`: crawler + `redis-frontier` CPU falls off the cliff.
- Kafka UI: `crawlers` / `crawlers-backoff` groups show members
  again once drains stop hogging the loop.
- If CPU stays pinned and logs show `Kafka broker unreachable`,
  the workers are crashlooping — a separate wiring issue, not this.
