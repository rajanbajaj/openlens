# Release plan: v1.1.21 (redis-frontier host port off agetech's :6380)

Target: release server (self-hosted runner `openlens-release`).
Mechanism: Actions -> release -> Run workflow (`services: all`,
`ref: v1.1.21`). Tag pushes never deploy. Agetech needs no
redeploy (lightweight stack untouched, code unchanged).

## Why

v1.1.20's main deploy failed in `Build and start selected
services`: `redis-frontier` could not bind host `127.0.0.1:6380`
(port already allocated). That port belongs to the agetech
stack's `redis` (separate project, same host, `REDIS_PORT=6380`
per `release-agetech.yml`). Main's `redis-frontier` container
did not exist before the deploy, so compose tried to create it
and hit the collision. The backend/frontend/crawler recreates
from that run are in place; only the start phase aborted, so
this re-run converges the stack without touching volumes.

## What's in this release

- `deploy/local/docker-compose.yml`: `redis-frontier` host port
  default `6380` -> `6381` (container port and service DNS
  unchanged, so no app config changes). Pinned via
  `REDIS_FRONTIER_PORT` when set — if the server's `release.env`
  pins `6380`, update it to `6381` instead.
- `deploy/local/.env.example`: documents `REDIS_FRONTIER_PORT`.
- `docs/wiki/Architecture.md`: port table/diagram follow.
- No code, settings, or volume changes; agetech stack untouched.

## Pre-release checklist

- [x] Gitleaks: no new findings (commit hook; compose/docs only).
- [ ] Server `release.env` does not pin `REDIS_FRONTIER_PORT=6380`
  (re-run tells us: same bind error means pinned — update it).
- [ ] No `-v` volume wipes; plain `up` converges.

## Release steps

1. Commit the fix, then the release commit (version bump); push
   `main`, then tag `v1.1.21` and push the tag (tags never move).
2. Actions -> release -> Run workflow (`services: all`,
   `ref: v1.1.21`); watch the `release-production` run.
3. Gates: `/healthz`, search probe, both frontends, workers/data.

## Post-deploy verification (on the server)

- `docker compose ps` shows `redis-frontier` up on `:6381`
  alongside agetech's redis on `:6380`.
- Enqueue `https://fossbytes.com` with depth 10: fetches instead
  of `depth cap exceeded`.
- `GET /api/v1/frontier/settings` still shows `default_max_depth: 2`.
