# Release plan: v1.1.19 (env-gated site login, agetech fresh DB)

Target: release server (self-hosted runner `openlens-release`).
Mechanism: Actions -> release-agetech -> Run workflow,
`ref: v1.1.19`, `reset_data: true` (fresh DB + index).

## What's in this release

- **Env-gated site login**: `OPENLENS_SITE_PASSWORD` set on a
  deployment locks the query surface (`POST /api/v1/search`,
  `GET /api/v1/suggest`, `POST /api/v1/agent/chat` require the
  `X-Site-Password` header, 401 otherwise); the frontend shows a
  lock screen until unlocked (tab-scoped sessionStorage token,
  wrong-password inline error, nav Lock button). New public
  `GET /api/v1/site/status` reports the gate state. Empty password
  (main stack) keeps search fully public — same build, no drift.
- **Agetech fresh start**: `release-agetech` gained a `reset_data`
  input that wipes only the `openlens-agetech-*` volumes before the
  rebuild; the search health gate reuses the deployed password
  (masked) so it probes the real locked path.
- Server-side prerequisite (not in repo): `OPENLENS_SITE_PASSWORD`
  in `/home/rajan/servers/agetech.env`.
- 8 new tests (backend gate matrix, frontend token/status/401,
  SiteLock, App lock flow incl. axe coverage).

## Release steps

1. Commit the feature, then the release commit (version bump); push
   `main`, then tag `v1.1.19` and push the tag (tags never move).
2. Actions -> release-agetech -> Run workflow (`ref: v1.1.19`,
   `reset_data: true`); watch the run.
3. Gates: `/healthz`, locked search probe (401 without password,
   200 with), lock screen in a browser, both frontends.

## Post-deploy verification (on the server)

- `GET /api/v1/site/status` shows
  `{"auth_required": true, "authorized": false}`.
- Search without the header 401s; the UI shows the lock screen and
  unlocks with the password from `agetech.env`.
- Fresh DB: no documents/queue rows carried over.
