# Release plan: v0.5.10 (backfill drains the whole backlog)

Target: release server (self-hosted runner `openlens-release`).
Mechanism: tag `v0.5.10` triggers
[.github/workflows/release.yml](../../.github/workflows/release.yml).

## What's in this release

- **Backfill paging fix**: the cutover replay paged offset 0
  forever, so the first pass sealed the migration after the first
  batch (prod: 1,000 of ~62k rows; rest stranded). Now uses offset
  pages plus bounded verification sweeps for rows shifted by
  concurrent terminal flushes. A capped pass still leaves the
  migration unsealed.
- **Stale seal already cleared on prod** (`fw:backfill:done` and
  lock deleted on the live DB 0), so the first fixed worker boot
  resumes the remaining ~59k rows. Dedup via the Redis seen set
  makes the ~3.7k already-replayed rows harmless.
- 1 new regression test (`test_backfill_pages_past_first_batch`);
  cap/resume test updated to the truthful added-count semantics.

## Pre-release checklist

- [ ] `git status` clean except this plan file.

## Release steps

1. Tag `v0.5.10` and push `main` + tag (tags never move).
2. Watch the `release` workflow (`concurrency: release-production`).
3. Gates: `/healthz`, frontier status, search probe, both frontends.

## Post-deploy verification (on the server)

- First worker log shows `backfill mirror→redis: N urls` with N
  in the tens of thousands (not 1,000).
- `fw:ready` jumps; admin live queue depth starts falling from
  ~62k; `frontier_mirror_lag_seconds` stays ≤ 5 s.
