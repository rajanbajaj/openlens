# Release plan: v0.5.8 (persistent vertical scaling, frontier RAM)

Target: release server (self-hosted runner `openlens-release`).
Mechanism: tag `v0.5.8` triggers
[.github/workflows/release.yml](../../.github/workflows/release.yml).

## What's in this release

- **Persistent vertical scaling**: the scale workflow's `cpus` /
  `memory` inputs now persist to `release.env` as
  `<SERVICE>_CPUS` / `<SERVICE>_MEM` (after the live `docker
  update` succeeds), and `deploy/local/docker-compose.yml` reads
  all 15 services' `mem_limit` / `cpus` from those vars with
  today's values as defaults. Same durability contract as
  horizontal scaling.
- **redis-frontier RAM 2 GB** (`maxmemory 1536mb`, `noeviction`
  kept) to hold the frontier hot path with headroom.
- **Crawler boot banner**: workers print
  `frontier backend=<..> store=<..> mirror=<on|off>` via `print`
  (the worker process wires no stdlib handlers, so `logger.info`
  was silently dropped).
- Release plan docs only (`docs/releases/`).

## Pre-release checklist

- [ ] `git status` clean except this plan file.
- [ ] No new required env vars; all bounds fall back to today's
  shipped values. No `-v` volume wipes.
- [ ] `docker compose config` resolves all 30 bounds identically
  except the frontier bump.

## Release steps

1. Tag `v0.5.8` and push `main` + tag (tags never move).
2. Watch the `release` workflow (`concurrency: release-production`).
3. Gates: `/healthz`, frontier status, search probe, both frontends.

## Post-deploy

- Crawler logs must show the backend banner; Dozzle finally
  reveals which frontier path is live.
- `scale` with `cpus`/`memory` should now survive the next
  redeploy (verify by re-running `docker compose config` on the
  server after a scale run).
