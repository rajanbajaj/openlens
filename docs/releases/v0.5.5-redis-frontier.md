# Release plan: v0.5.5 (Redis frontier hot path)

Target: release server (self-hosted runner `openlens-release`).
Mechanism: tag `v0.5.5` triggers
[.github/workflows/release.yml](../../.github/workflows/release.yml).

## What's in this release

- **Redis frontier hot path** (`frontier.backend: redis`, default
  stays `postgres`): `RedisFrontierStore` (leases/queues/heartbeats
  in Redis), write-behind `FrontierMirrorFlusher` to Postgres
  (staleness SLA ≤ `flush_interval_s`, default 5s), new
  `redis-frontier` compose service (AOF everysec, 512MB noeviction,
  port 6380). Ops reads stay on Postgres; rollback is a config flip.
- **Scale workflow**: `redis-frontier` added to the service list
  (singleton: `replicas=1` recreates, else rejected); vertical
  tuning works as for the other singletons.
- **README**: architecture diagram + Redis-hot-path notes.

## Pre-release checklist

- [ ] `git status` clean except this plan file.
- [ ] No new required env vars: compose defaults
  (`redis://redis-frontier:6379/0`, prefix `fw`, flush 5s) boot
  clean. `OPENLENS_FRONTIER_BACKEND` unset keeps the shipped
  Postgres path — zero behavior change on deploy.
- [ ] No `-v` volume wipes.

## Release steps

1. Tag `v0.5.5` and push `main` + tag (tags never move).
2. Watch the `release` workflow (`concurrency: release-production`).
3. Gates: `/healthz`, frontier status, search probe, both frontends.

## Post-deploy cutover (separate, manual)

The release alone does **not** move the hot path (default stays
`postgres`). To cut over:

1. On the server, add `OPENLENS_FRONTIER_BACKEND=redis` to
   `~/servers/release.env`.
2. Re-run the release workflow (selective deploy:
   `backend crawler crawler-backoff`) so the new env is picked up.
3. Watch `frontier_mirror_lag_seconds` (≤5s) and the frontier
   status gate; confirm Postgres master CPU drops.
4. Rollback: remove the flag, redeploy the same way. Redis leases
   TTL out; Kafka redelivers anything in flight.
