# Release plan: v0.5.9 (cutover backfill for Redis frontier)

Target: release server (self-hosted runner `openlens-release`).
Mechanism: tag `v0.5.9` triggers
[.github/workflows/release.yml](../../.github/workflows/release.yml).

## What's in this release

- **Cutover migration**: at boot, the first crawler worker replays
  the Postgres mirror's queued rows into the fresh Redis ready
  queue (`backfill_once`: `SET NX` claim, sealed with a done
  marker, capped passes resume later, never raises). Without it
  the fleet idles on an empty hot store while the dashboard shows
  a frozen queue — the exact state prod is in now (62k queued in
  the mirror, Redis empty).
- Worker prints `backfill mirror→redis: N urls` at boot
  (Dozzle-visible, same style as the backend banner).
- 5 new offline tests; attempts reset to the fresh-enqueue budget
  (documented at-least-once semantics).

## Pre-release checklist

- [ ] `git status` clean except this plan file.
- [ ] No new env vars; no config changes; no `-v` volume wipes.

## Release steps

1. Tag `v0.5.9` and push `main` + tag (tags never move).
2. Watch the `release` workflow (`concurrency: release-production`).
3. Gates: `/healthz`, frontier status, search probe, both frontends.

## Post-deploy verification (on the server)

- First worker log shows `backfill mirror→redis: N urls` with N
  in the tens of thousands; later workers log `0 urls`.
- `fw:ready` in redis-frontier becomes non-zero; the admin live
  queue starts draining (depth falls from ~62k).
- `frontier_mirror_lag_seconds` stays ≤ 5 s once crawling resumes.
