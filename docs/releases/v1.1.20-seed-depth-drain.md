# Release plan: v1.1.20 (explicit seed depth honored on every drain)

Target: release server (self-hosted runner `openlens-release`).
Mechanism: two manual dispatches on the same tag — Actions ->
release-agetech (`ref: v1.1.20`, no data reset) for the private
AgeTech instance, then Actions -> release (`services: all`,
`ref: v1.1.20`) for the main stack. Tag pushes never deploy.

## What's in this release

- **Explicit seed depth honored on every drain**: admin seeds
  stored above `default_max_depth` (e.g. fossbytes at depth 10,
  cap 2) no longer fail with `depth cap exceeded` when the drain
  carries no seed context (store backlog/idle `_drain_once`).
  `FrontierStore.update_depth` (SQLite, Postgres, Redis) forces
  the explicit seed depth on the API and Kafka worker seed paths
  (`enqueue` stays insert-only, `reseed` still revives without
  touching depth); the crawler self-roots over-cap preloaded rows
  (discovered links are push-gated, so only explicit seeds can
  exceed the cap) while under-cap rows keep absolute gating.
- 3 new tests (store depth overwrite, API re-paste depth update,
  rows-only deep-seed drain).

## Release steps

1. Commit the fix, then the release commit (version bump); push
   `main`, then tag `v1.1.20` and push the tag (tags never move).
2. Actions -> release-agetech -> Run workflow (`ref: v1.1.20`,
   `reset_data: false` — keep the agetech index); watch the run.
3. Actions -> release -> Run workflow (`services: all`,
   `ref: v1.1.20`); watch the `release-production` concurrency run.
4. Gates: `/healthz`, frontier status, search probe, frontends
   (agetech on its ports with the site password, main public).

## Post-deploy verification (on the server)

- Enqueue `https://fossbytes.com` with depth 10: fetches instead
  of `depth cap exceeded`; re-pasting at a new depth updates the
  stored row.
- `GET /api/v1/frontier/settings` still shows `default_max_depth: 2`.
- Agetech index intact (document counts carried over, no reset).
